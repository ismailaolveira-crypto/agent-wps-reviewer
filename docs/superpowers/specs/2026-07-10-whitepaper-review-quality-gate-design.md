# 白皮书批注质量门与历史风格对齐设计

日期：2026-07-10
关联规格：`2026-07-10-agent-reviewer-ui-active-document-design.md`
适用项目：2026 年《网络安全人才实战能力报告-AI赋能篇》
状态：方案 2 已由用户确认，等待书面规格复核

## 1. 问题与结论

当前 bridge 只要求每条建议包含原文锚点和批注文本。正式 Agent 入口会校验文档句柄与版本，但不校验以下内容：

- 问题是否在完整上下文中真实存在；
- 批注是否服务当前小节任务和本项目修改目的；
- 数据、跨段重复、编号冲突或历史风格判断是否有证据；
- 作者是否能按批注直接完成修改；
- 候选意见是否经过用户选择和最终文本预览；
- Agent 是否按 2022-2024 年同系列白皮书的内容风格进行比对。

因此，锚点可以技术上定位成功，但批注的判断仍可能错误。定位器只能回答“这段文字在哪里”，不能回答“这条意见是否成立”。

本设计采用三层质量门：

1. Skill 工作流门：限制审稿范围、候选数量、人工选择和最终预览。
2. 语义证据门：每条意见必须声明具体问题、影响、处理动作、修改目的和反证检查结果。
3. 文档定位门：bridge 在内存中核对锚点、上下文和当前版本，拒绝无法唯一定位的建议。

三层全部通过后，建议才能进入 WPS 侧边栏。

## 2. 修改目的

所有正式批注至少服务一个明确目的，并同时满足“可执行”和“降低审稿成本”两个基础要求。

| 代码 | 修改目的 | 判断标准 |
|---|---|---|
| `chapter-focus` | 让各章和小节完成自己的核心任务 | 段落与章节问题一致，不跑题、不跨章抢结论 |
| `evidence-accuracy` | 保证事实、数据和结论可靠 | 口径、分母、来源和结论边界可核验 |
| `structure-logic` | 解决结构、编号和论证关系问题 | 标题、段落、图表和结论之间关系明确 |
| `compression` | 压缩重复、空泛和无效铺垫 | 保留证据与判断，不做机械删句 |
| `anti-ai-tone` | 去除 AI 腔和宣传腔 | 使用明确主体、机制、证据和边界 |
| `historical-style` | 保持与 2022-2024 年同系列白皮书风格一致 | 依据历史风格规则，而非凭“像白皮书”主观判断 |
| `human-boundary` | 保留编委对强判断、重大删改和传播表达的决定权 | 不越权替领导或编委做最终判断 |

每条意见还必须满足：

- 精确指出原文位置；
- 说明具体问题，而非只写“建议优化”；
- 说明问题如何妨碍本节任务、事实准确性或历史风格一致性；
- 给出删除、合并、压缩、替换、弱化、移动、核验或编委确认等直接动作；
- 修改收益大于作者理解和处理该批注的成本。

不能满足这些条件的内容不进入候选列表，更不能进入 WPS。

## 3. 2022-2024 历史风格基线

### 3.1 权威来源

本项目使用以下已确认资料作为风格依据：

- 2022 年《网络安全人才实战能力白皮书》内参版；
- 2023 年《网络安全人才实战能力白皮书-人才评价篇》；
- 2024 年《网络安全人才实战能力白皮书-安全测试评估篇》；
- `whitepaper-chief-editor` 项目包中的 `style-profile.md`；
- 2024 年最终稿、人工校对稿和修订意见，用于提炼作者可执行的批注语言。

原始 PDF/DOCX 用于建立和复核风格画像。GitHub 发布包不依赖本机绝对路径，而是携带经过来源指纹记录的精简风格规则。

### 3.2 内容风格规则

仓库内置风格画像至少包含以下稳定规则，并给每条规则分配可引用的 `styleRuleId`：

- 判断在前，解释随后，再给数据或案例；
- 不用大段背景铺垫延迟核心判断；
- 使用正式、克制的行业研究语言；
- 调研结论限定为受访样本，不外推成全国事实；
- 章节围绕一个主问题推进，段落之间有递进关系；
- 保留三级标题和同系列报告的结构连续性，但不机械复刻八股结构；
- 传播性判断必须可引用、有证据、有边界，并由人确认；
- 避免“深刻重塑”“全新生态闭环”“全面赋能高质量发展”等空泛表达。

风格类意见必须提供 `styleRuleIds`。没有对应规则、只有个人语言偏好的批注不得提交。

### 3.3 风格一致性边界

历史白皮书是内容组织和表达方式的基线，不要求 2026 稿件复制旧报告句式。以下情况不能以“历史风格”为由强制修改：

- 新主题需要新的能力框架或术语；
- 当前章节逻辑已经更清晰；
- 旧报告表达与当前数据或风险边界冲突；
- 只是审稿人的个人措辞偏好，不影响理解、证据或系列连续性。

## 4. 正式审稿流程

### 4.1 小节级候选

- 默认一次只审一个二级小节或内容密集的三级小节。
- 每轮 3-7 条候选，硬上限 8 条。
- 候选意见在聊天中使用 `【位置】/【问题】/【建议改为】` 三行格式。
- 不因一句话“还能润色”就生成候选；必须先说明本节要完成什么任务。

### 4.2 人工选择与最终预览

1. 用户选择、删除或改写候选编号。
2. Agent 生成包含精确锚点和自然批注语言的最终预览。
3. Agent 将最终预览过的建议提交到 WPS 侧边栏。
4. 用户在侧边栏点击“接受”，作为生成真实 WPS 批注的明确授权。

提交侧边栏不修改正文，也不立即生成 Word 批注。侧边栏“接受”仍是唯一的 WPS 写入动作。

### 4.3 反证检查

最终预览前，Agent 必须重新读取锚点所在段、前一标题、相邻段和必要的跨段参照，并逐条检查：

- 前文是否已经提供了批注声称缺失的标题、定义、证据或边界；
- 后文是否已经完成了批注要求补充的内容；
- 所谓重复是否承担不同段落功能；
- 所谓编号错误是否只是目录、题注或交叉引用的不同编号体系；
- 所谓历史风格偏差是否有明确 `styleRuleId`；
- 删除或压缩后是否会破坏证据链、过渡或三级标题结构。

只要完整上下文能推翻问题判断，该候选必须淘汰。此前把已有 `4.3.4` 标题误判为标题缺失，属于反证检查未执行的典型失败。

## 5. 正式提交契约

`submit_wps_suggestions` 使用批量正式契约。批次结构如下：

```json
{
  "documentHandle": "wpsdoc_xxx",
  "revisionToken": "sha256:xxx",
  "sourceAgent": "codex",
  "reviewProfile": "whitepaper-chief-editor-v1",
  "reviewScope": {
    "sectionId": "4.3.3",
    "sectionTitle": "AI辅助区块链安全运营与告警研判",
    "sectionGoal": "说明 AI 如何改变该场景的工作方式和人才评价要求"
  },
  "workflow": {
    "stage": "final-previewed",
    "candidateRoundId": "round_xxx",
    "approvedCandidateIds": ["candidate_1"]
  },
  "styleBaseline": {
    "profile": "network-security-talent-whitepaper-2022-2024",
    "version": "1"
  },
  "suggestions": [
    {
      "candidateId": "candidate_1",
      "category": "duplicate-compression",
      "anchorText": "精确原文",
      "contextBefore": "相邻前文",
      "contextAfter": "相邻后文",
      "comment": "自然、具体、可执行的最终批注文本",
      "quality": {
        "issue": "具体问题",
        "impact": "该问题如何影响本节任务或读者判断",
        "action": "compress",
        "actionStatement": "建议压缩重复说明，把篇幅留给本节核心判断。",
        "purposeCodes": ["compression", "chapter-focus"],
        "keyTerms": ["重复说明", "核心判断"],
        "evidenceIds": [],
        "styleRuleIds": [],
        "verification": {
          "fullContextChecked": true,
          "counterEvidenceChecked": true,
          "result": "supported",
          "documentEvidenceExcerpt": "支持问题判断的正文或相关段落片段",
          "relatedExcerpts": []
        }
      }
    }
  ]
}
```

### 5.1 类别

正式类别固定为：

- `data-fact`
- `structure-logic`
- `duplicate-compression`
- `style-alignment`
- `anti-ai-tone`
- `numbering-figure-table`
- `committee-confirmation`

### 5.2 动作

正式动作固定为：

- `delete`
- `merge`
- `compress`
- `replace`
- `soften`
- `move`
- `verify`
- `confirm`

数据事实类意见必须提供 `evidenceIds`。风格对齐类意见必须提供 `styleRuleIds`。需要编委判断的意见必须使用 `confirm`，不能伪装成确定事实。

`documentEvidenceExcerpt` 和 `relatedExcerpts` 只记录当前文档中的问题证据。问卷、报告、网页或数据库等外部依据通过 `evidenceIds` 及项目包中的证据索引引用，不能把外部来源文本伪装成当前正文。

### 5.3 内容一致性字段

- `keyTerms` 包含 1-5 个可在当前正文中核验的关键术语，至少一个术语必须足够具体，不能使用“本段”“内容”“文字”“问题”等指代词充数。
- `issue`、`impact` 和最终 `comment` 必须各自引用至少一个 `keyTerms`，确保三者讨论的是同一处真实问题。
- `actionStatement` 是最终 `comment` 中原样出现的肯定式动作子句，必须以“建议”或“请”开头，并与 `action` 一致。
- bridge 在正文定位门中验证 `keyTerms` 确实来自当前版本正文；纯契约校验不把 Agent 自报的关键术语当成事实。

类别与修改目的允许交叉，但必须有合理联系。例如结构问题可以通过合并或压缩解决；风格类意见必须包含 `historical-style`；数据事实类意见必须包含 `evidence-accuracy`；编委确认类必须包含 `human-boundary`。

## 6. 校验职责

### 6.1 Skill 和 Agent 负责

- 理解章节任务；
- 读取历史风格画像；
- 生成候选、等待选择和最终预览；
- 完整上下文与反证检查；
- 数据证据和历史风格规则的真实引用；
- 判断意见是否值得占用审稿人的时间。

### 6.2 bridge 负责

- 校验正式契约字段、枚举、批次上限和同一小节范围；
- 校验候选 id 已包含在本批次批准列表中；
- 校验数据类和风格类意见有对应依据 id；
- 校验文档句柄与版本指纹；
- 按需在内存中读取当前正文，确认锚点存在；
- 锚点重复时使用前后文确认唯一位置；
- 确认 `documentEvidenceExcerpt`、`relatedExcerpts` 和定位上下文确实来自当前正文；
- 失败时整批拒绝，不产生半批次脏数据。

bridge 不能独立证明一个行业判断在语义上正确。它只能验证 Agent 提供的审稿过程证据是否完整、是否能在当前文档中落地。文档语义正确性依靠 Skill 的两遍审稿和用户选择共同保证，不能虚假宣传成“服务端自动理解正确”。

`workflow` 字段是可信本机 Agent 写入的审计记录，不是对用户行为的密码学证明。bridge 负责拒绝缺少审批记录的请求；Skill 负责真实执行候选、选择和预览流程；真实 Word 写入仍由用户点击侧边栏“接受”完成。

## 7. 旧入口与 GitHub 可用性

### 7.1 正式入口

- GitHub 用户安装后默认使用 `get_active_wps_document`、`read_wps_document` 和 `submit_wps_suggestions`。
- MCP 工具说明明确要求先调用仓库内置 Skill。
- 正式提交只接受 `whitepaper-chief-editor-v1` 契约。

### 7.2 兼容入口

- `submit_wps_suggestion` 和 `POST /api/suggestions` 不再作为正式白皮书入口。
- 默认禁止旧入口创建建议。
- 只有显式设置开发兼容开关时才允许旧入口，用于协议联调和非白皮书测试。
- 兼容建议标记为 `legacy-unverified`，不得混入正式白皮书待处理列表。

### 7.3 仓库内置 Skill

发布包新增可安装 Skill，包含：

- 审稿工作流；
- 修改目的与章节问题地图；
- 2022-2024 内容风格画像及来源指纹；
- 正式提交契约；
- 反证检查清单；
- MCP 调用顺序和错误恢复方式。

本地安装脚本同时安装 bridge、WPS 加载项配置和 Skill。所有文档与脚本使用仓库相对路径或运行时解析路径，不写死开发者 `/Users/...` 路径。

## 8. 历史不合格记录隔离

当前 `data/review-store.json` 中 17 条历史建议均没有正式审稿 profile 和证据字段。处理方式：

1. 生成带日期和 SHA-256 的隔离备份；
2. 备份建议、关联验收事件和原始状态；
3. 从活动 ReviewStore 中移除这 17 条建议及其关联事件；
4. 保留文档 session 元数据；
5. 输出隔离清单和恢复命令；
6. 不启动 WPS，不删除真实 WPS 文档中的既有批注。

隔离脚本默认先执行 dry-run，只有显式 `--apply` 才修改活动数据。用户已确认采用该隔离方案。

## 9. 错误处理

- 缺少审稿 profile：提示 Agent 调用仓库 Skill 后重新生成。
- 批次超过 8 条或混入不同小节：整批拒绝并要求拆分。
- 缺少问题、影响、动作或修改目的：整批拒绝，返回具体条目 id。
- 数据类缺少证据：拒绝该批次，不允许用空泛“建议核实”绕过。
- 风格类缺少历史规则：拒绝并提示选择已定义 `styleRuleId`。
- 反证检查未完成或结果不是 `supported`：拒绝。
- 锚点不存在：拒绝提交，不进入侧边栏冲突状态。
- 锚点重复且上下文不能唯一定位：拒绝并要求扩大锚点或补充上下文。
- 正文版本变化：返回过期错误，要求重新读取和复核全部建议。
- 正文读取超时：不保存任何建议。

错误响应使用中文可行动信息，不返回内部堆栈。

## 10. 测试与验收

### 10.1 自动化测试

- 正式批次缺少任一质量字段时失败；
- 数据、风格和编委确认类别执行各自附加约束；
- 一轮超过 8 条、跨小节或候选未批准时失败；
- 唯一锚点通过，重复锚点无上下文失败，正确上下文通过；
- `documentEvidenceExcerpt` 或 `relatedExcerpts` 不在当前正文中时失败；
- 完整上下文包含反证时，Skill 级验证样例必须淘汰该意见；
- 版本变化时整批不入库；
- 批次中一条失败时零条入库；
- 旧入口默认禁止，开发兼容开关可用且标记 `legacy-unverified`；
- Skill、风格画像和 schema 被包含进 release；
- release 和安装说明不存在开发者绝对路径；
- 隔离 dry-run 不修改文件，`--apply` 生成可恢复备份并清空活动脏记录；
- 原有 UI、拒绝撤销、接受防重复和 WPS 适配器测试继续通过。

### 10.2 后台浏览器验收

- 只向模拟队列注入通过质量门的建议；
- 在 320、360、420、480px 下检查卡片、详情和三项操作；
- 质量元数据不挤占侧边栏主要阅读空间；
- 失败批次不出现在待处理或全部视图；
- 不启动、不聚焦、不控制 WPS。

### 10.3 真实 WPS 验收

真实 WPS 验收仍由用户主动打开 WPS 后可见地完成：

- 定位到与上下文一致的原文；
- 接受后只生成一条真实批注；
- 批注语言与人工样本一致；
- 批注确实对应当前小节任务和修改目的；
- 风格类意见能追溯到 2022-2024 风格规则；
- 后台操作不切换文档、不弹窗、不抢焦点。

后台自动化通过不能替代真实 WPS 验收。

## 11. 完成标准

只有同时满足以下条件，才能认为本质量门完成：

- GitHub 发布包包含可安装 Skill、风格画像和正式 schema；
- 新安装用户无需本机私有路径即可调用 Skill 和 MCP；
- 正式入口拒绝缺少小节审稿、人工选择、最终预览和反证检查审计记录的建议；
- 文档锚点在提交前已经通过当前版本正文核验；
- 所有正式意见都能追溯到修改目的，风格意见能追溯到 2022-2024 规则；
- 17 条历史不合格记录已生成可恢复隔离备份并退出活动队列；
- 自动化、后台浏览器测试通过；
- 真实 WPS 项目仍保持待用户主动打开后验收的明确状态。
